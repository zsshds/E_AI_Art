## Context

当前项目已经提供系统设置页，用于配置第三方 AI 平台的基础接入参数，但图像调用链路中的关键接口仍然部分写死在后端图像客户端中。例如文生图与编辑图共用固定任务提交路径，任务轮询、聊天补全、模型获取等接口也只有部分暴露到设置层。这在接入 OpenAI 兼容但接口路径不完全兼容的平台时，会直接导致请求 404 或只能通过改代码适配。

这次变更跨越前端设置页面、后端设置存储、后端图像客户端和默认配置初始化逻辑，属于典型的跨模块配置能力扩展。设计需要同时考虑：
- 管理员配置体验是否足够直观；
- 现有环境能否在不完整迁移时保持可用；
- 各接口既支持基于 `api_base_url` 的相对 Path，也支持直接填写完整 URL；
- 文生图与编辑图接口未来继续分化时不需要再次大改结构。

## Goals / Non-Goals

**Goals:**
- 为图像相关主要调用链路提供独立可配置的接口字段。
- 支持每个接口字段填写相对 Path 或完整 URL，并在运行时统一解析。
- 将文生图与编辑图的接口配置解耦。
- 保持当前已有配置的默认值与回退行为，降低升级成本。
- 让系统设置变更保存后立即生效，无需重启服务。

**Non-Goals:**
- 不在本次引入多供应商模板切换机制。
- 不重构整个任务调度模式或同步/异步调用架构。
- 不将接口配置收敛成单个 JSON 文本字段。
- 不重新设计模型管理或风格配置业务逻辑。

## Decisions

### 1. 为每类关键接口提供独立设置键
**Decision**：在现有设置体系上继续扩展离散字段，而不是改成单一 JSON 配置。

**Rationale**：
- 当前前后端已围绕扁平键值对设置模型实现，增量扩展成本最低。
- 系统设置页直接增加输入框，符合用户已经明确选择的交互方式。
- 单独字段更容易做默认值回退、表单校验和问题排查。

**Alternatives considered**：
- 单个 JSON 配置：灵活但对运营人员不友好，也提高校验复杂度。
- 供应商模板：适合后续演进，但本次先解决路径可配问题，避免范围扩大。

### 2. 引入统一的“接口地址解析”规则
**Decision**：后端对每个接口配置统一采用以下解析规则：
- 若配置值以 `http://` 或 `https://` 开头，则按完整 URL 直接请求；
- 否则将其视为相对 Path，与 `api_base_url` 组合成最终请求地址。

**Rationale**：
- 同时满足标准 OpenAI 兼容平台与路径特殊的平台。
- 复用现有 `baseURL + path` 心智模型，同时为例外平台留出口。
- 将 URL 解析集中在图像客户端内部，避免各调用点重复判断。

**Alternatives considered**：
- 仅支持相对 Path：无法覆盖网关转发、跨域代理或多域名接口平台。
- 每项仅支持完整 URL：会弱化 `api_base_url` 的价值，增加配置重复。

### 3. 文生图、编辑图、轮询、聊天补全、模型获取分别配置
**Decision**：将主要图像调用链路拆成独立配置项，至少覆盖：
- 文生图提交接口
- 编辑图提交接口
- 任务轮询接口
- 模型列表接口
- 聊天补全接口

**Rationale**：
- 当前 404 的直接原因就是不同接口被错误复用。
- 第三方平台常常对生成、编辑、轮询采用不同路径策略。
- 独立字段可让后续问题排查更快定位到具体链路。

**Alternatives considered**：
- 文生图/编辑图共用一个提交接口：短期简单，但无法满足用户已确认的独立配置诉求。
- 完整按供应商抽象出接口对象：设计过重，不适合本次变更规模。

### 4. 保留默认值与兼容回退
**Decision**：新增字段未配置时，后端回退到当前默认路径；已有字段继续兼容现有存量数据。

**Rationale**：
- 避免已有部署升级后因为新字段为空而整体不可用。
- 允许管理员逐步完成迁移，而不是一次性补齐全部设置。

**Alternatives considered**：
- 强制所有新字段必填：实现简单，但会造成升级阻塞。
- 完全无默认值：错误更显式，但对当前用户不友好。

## Risks / Trade-offs

- **[风险] 配置项数量增加后，系统设置页变得更复杂** → **缓解**：按“基础连接配置 / 图像接口配置 / 模型配置”分组展示，并提供清晰说明文案。
- **[风险] 不同接口字段混用完整 URL 与相对 Path，容易出现拼接错误** → **缓解**：统一解析逻辑，并通过测试覆盖末尾斜杠、前缀协议、空值回退等场景。
- **[风险] 第三方平台并非任务轮询模式，当前架构仍可能不兼容** → **缓解**：在本次设计中保留该问题为显式开放问题，不在实现阶段隐式扩展协议。
- **[风险] 旧字段与新字段的默认关系处理不清晰，可能引入回归** → **缓解**：在客户端集中定义默认常量与优先级顺序，并补充回归测试。

## Migration Plan

1. 扩展设置数据模型与默认值初始化逻辑，新增所需配置键。
2. 扩展系统设置 API 的允许字段与前端类型定义。
3. 在系统设置页增加新增输入项，并按分组组织说明。
4. 重构图像客户端的配置解析逻辑，统一处理完整 URL / 相对 Path。
5. 让文生图、编辑图、轮询、聊天补全、模型获取分别读取对应配置。
6. 补充单元测试与关键回归测试，验证旧配置和新配置都能工作。
7. 发布后管理员可按需补充新字段；若未补充，则系统继续使用默认回退。

回滚策略：若新配置逻辑引发问题，可回退到旧版本代码；由于新增设置键不影响旧版本读取，数据库中的新增键不会阻碍回滚。

## Open Questions

- 是否需要在本次实现中顺手为“查看最终请求 URL”提供调试可见性（如日志或测试接口）？
- 新平台是否仍然严格遵循“提交任务 -> 轮询结果”的异步模式，还是后续需要支持同步响应模式？
- 是否需要对空字符串配置做特殊处理（视为未配置）并统一回退？
